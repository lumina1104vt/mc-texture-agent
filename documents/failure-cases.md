# 失敗情境（Failure Cases）

模型：`dsv4p-qwen3.5:9b`（Ollama）。以下都是實測中真的發生過的情況，不是假設。原始軌跡在 `documents/traces/`。

## 失敗 1：模型自己做 uint8 運算，顏色溢位

- **失敗狀況**：要求畫礦石時，圖上出現青色、黃綠色的雜點。
- **原因**：模型直接對 `uint8` 陣列做減法，`25 - 50` 變成 `231`（環繞），而不是 0。
- **解決方法**：寫 `texture_kit`，所有顏色運算改用 Python int 並限制在 0–255（`shade`）；系統提示詞明確禁止直接對 uint8 陣列做運算。有單元測試保護。

## 失敗 2：礦石是黑底，沒有石頭

- **失敗狀況**：「紅寶石礦石」畫成黑色背景上幾顆紅點，不像礦石。
- **原因**：模型用 `new_canvas((0,0,0))` 起手，再蓋上參考圖的 ASCII 圖；參考圖大部分是透明的（只含礦物，不含底色）。
- **解決方法**：skill 加入礦石規則（先用底材色鋪滿整張，再蓋礦物簇；參考圖大部分透明就是疊加圖，底色要自己鋪）；加入「畫完回頭看」迴圈，成品存檔後讓模型看圖對照需求，不對就重畫。

## 失敗 3：沒匯入的 `random`，以及數字元數錯

- **失敗狀況**（`traces/run1-before-tool-redesign.txt`）：「紅寶石礦石」跑了 9 步、約 17 分鐘（1,040 秒）、累計輸入 87,177 token，其中 5 步失敗：
  - 步驟 1、5：`InterpreterError: The variable random is not defined`（想撒顆粒但沒 import；步驟 2 自己說要改掉，步驟 5 又犯）。
  - 步驟 3：`ValueError: Character 'D' in row 1 is not in the palette`（圖案用了調色盤沒有的字元）。
  - 步驟 7：`ValueError: All rows must have the same length`（每列字元數不一致）。
  - 步驟 6：程式碼是空的，白花 135 秒（原因不明）。
- **原因**：`stamp_ascii` 要求模型一格一格數字元，這是 9B 最弱的地方；而 `texture_kit` 沒有提供「撒顆粒」，模型只好自己用 `random`。
- **解決方法**：
  1. 錯誤訊息加上具體建議（直接給補好 `.` 的列），步驟 8 就是照這個修好的。
  2. 把 `texture_kit` 函式放進 Agent 的狀態，不必 import 就能用。
  3. 根本解法：新增 `speckle`（撒顆粒）與 `gem_cluster`（自動著色的礦物簇），模型不用再數字元、也不用 `random`。
- **改善結果**（`traces/run2-after-tool-redesign.txt`）：同一個需求，2 步、72.6 秒、輸入 9,666 token、零錯誤。

## 失敗 4：模型用 `print()` 跟使用者講話，陷入迴圈

- **失敗狀況**：使用者打招呼或追問時，Agent 把回覆寫成 `print("…")`，但 print 輸出只回到模型自己的下一步，使用者看不到，它就接著開始下一步，一直空轉到步數上限。
- **原因**：CodeAgent 預設只能用程式碼溝通，沒有「直接說話」的出口；且每次訊息都重設記憶，無法對話。
- **解決方法**：`TextureCodeAgent` 覆寫單步邏輯，沒有程式碼區塊的回覆視為最終答案並結束這一輪；改為不重設記憶（`reset_agent_memory=False`）；提示詞新增「Talking to the user」規則。有單元測試保護。

## 失敗 5：模型失控生成，一個步驟跑了一個多小時

- **失敗狀況**：批次測試在 T09 的第 8 步停了一個多小時沒有結果。Ollama 日誌顯示同一個請求（task 37711）已生成超過 24,000 個 token，仍在增加，速度約 6 token/秒；`ollama ps` 則顯示模型 `Stopping...`、上下文 262144。
- **原因**：9B 陷入無限重複輸出。當時程式沒有設定單次輸出上限與請求逾時，上下文又開到 26 萬，沒有任何機制能讓它停下來。
- **解決方法**：模型呼叫加上單次輸出上限（`MAX_OUTPUT_TOKENS`，預設 8192）與請求逾時（`LLM_TIMEOUT`，預設 600 秒，不自動重試）；批次測試改為非串流（逾時才是整體時限），單一案例失敗記成當機並繼續下一個，每跑完一個案例就寫入結果。串流（對話介面）時只有輸出上限能擋住失控生成。
- **附帶損失**：這次中斷時批次測試是跑完才寫檔，容器又是 `--rm`，T01–T08 的步數與耗時統計因此遺失（圖還在），這也是改為即時寫入的原因。

## 失敗 6：物品與機器畫不出形狀（批次實測）

- **失敗狀況**：10 個案例的人工評分 0/10 及格。三種礦石勉強能看；泥土、木板、玻璃、鐵劍、藥水瓶、齒輪、發電機完全看不出來（圖與逐案例觀察見 `test-results.md`）。例如鐵劍只畫出貼在左邊緣的細直條，藥水瓶只是一根紅色長方塊，齒輪是一個有方孔的方塊。
- **原因**：礦石有專用函式（`speckle`、`gem_cluster`）替模型處理形狀與著色；其他東西模型只能自己用座標與 ASCII 畫輪廓，9B 做不到。評審迴圈（最多 2 次重畫）也抓不出這些明顯的問題，多數案例重畫後仍然不好。
- **另一個小問題**：T09 模型把物品（齒輪）存成 `kind="block"`，規則裡沒有教它怎麼判斷 block 或 item（原因是推測，未驗證）。
- **解決方法**：目前沒有。可能方向（未實作）：為常見形狀（劍、瓶、齒輪等）提供現成的輪廓函式、或換更強的模型；後者受限於速度無法採用。

## 尚未解決的限制

- **語意誤解**：9B 曾把「紅寶石」當成「紅石（redstone）」畫。目前沒有專門的機制，只能靠使用者重新描述。
- **評審次數用完就收工**：`REVIEW_ROUNDS` 用完後，模型直接把最後一版交出，沒有再檢查（run1 步驟 9）。
- **空程式碼的一步**：run1 步驟 6，原因未查明。
- **速度**：9B 每步 20–190 秒；步數越多越慢，是目前最大的使用體驗限制。
